**A. `CategoryService` has zero test coverage at any level.**
- Source: verification-gap.
- Evidence: no `CategoryServiceTests.cs` exists anywhere in the repo (`tests/Application.Tests/Services/` holds only `ProductServiceTests.cs`, Story 1.6's suite). `MutationEndpointsAuthTests.cs`'s Category requests carry no auth cookie, so the JWT challenge rejects them before any `CategoryService` code runs — confirmed by that test file's own doc comment. No test anywhere instantiates `CategoryService` or calls `DeleteAsync`/`CreateAsync`/`UpdateAsync`.
- Demonstrated: inverting the `HasProductsAsync` branch in `CategoryService.DeleteAsync` (`src/Application/Services/CategoryService.cs:68-74`) — the exact business rule Story 1.2 exists to implement (categories with products can't be deleted, 409 not a cascade) — would ship a passing `dotnet test` run.
- Disposition: **fix now** as a test addition, mirroring `ProductServiceTests.cs`'s Moq'd `IUnitOfWork`/`ICategoryRepository` pattern.
- Upstream lesson: Story 1.6 added a unit-test suite for `ProductService` specifically; `CategoryService` — built one story earlier, with the same shape and the same untested business rule — never got the same treatment. When a "write tests for X" story exists, check whether a structurally identical sibling needs the same pass.

**B. `CorrelationIdMiddleware`'s one load-bearing guarantee — surviving error responses — has no test.**
- Source: verification-gap, independently corroborated by acceptance-auditor's finding D below.
- Evidence: `CorrelationIdMiddleware.cs`'s own comment states the `OnStarting`-deferred header write exists specifically so `X-Correlation-Id` "survives on every response, including error ones," past `UseExceptionHandler`'s `Response.Clear()` — and says this was "confirmed by forcing a real unhandled exception against the running app," i.e. verified manually, once, by hand. `grep -rin "correlation" tests/` returns zero matches anywhere in the repo.
- Demonstrated: reverting the `OnStarting` deferral to an immediate header write (the exact regression the code comment warns against) would pass every existing test.
- Disposition: **fix now** as a test addition — an integration test via `WebApplicationFactory<Program>` that forces a 500 and asserts `X-Correlation-Id` is still present on the response.
- Upstream lesson: "verified manually once, by hand" is not the same as "regression-tested" — a finding this project has now hit multiple times across different epics (the Epic 2 code review found the identical pattern for the JWT `OnChallenge` ProblemDetails envelope).

**C. `spec-1-4`'s frozen boundary text contradicts its own shipped implementation, with no recorded renegotiation.**
- Source: acceptance-auditor, verified directly against the spec file.
- Evidence: `spec-1-4-correlation-id-structured-logging.md`'s frozen `Boundaries & Constraints` (line 21) states two "Always" rules: the middleware is "registered immediately after `UseExceptionHandler()`," and the correlation-ID value "is set on the response headers before the downstream pipeline runs." The shipped code does the opposite on both counts — `CorrelationIdMiddleware.cs`'s own doc comment says it's registered *before* `UseExceptionHandler()`, and the header write happens inside an `OnStarting` callback (i.e. after the downstream pipeline runs), for good, explained reasons (surviving `Response.Clear()` on a 500). The spec's own non-frozen "Suggested Review Order" section (lines 65, 70) explains and endorses this reversal — but unlike specs 2.1/2.2/2.3, which each carry an explicit `## Spec Change Log` section recording exactly this kind of approved deviation from frozen intent, `spec-1-4` has no such section at all (`grep -n "^## "` on the file confirms — no Spec Change Log heading exists).
- Disposition: **propose spec reconciliation** — add a Spec Change Log entry to `spec-1-4` recording the registration-order and header-write-timing deviations and why they're correct, matching the pattern already established for later stories. Human applies (touches the project's frozen-intent contract).
- Upstream lesson: the Spec Change Log mechanism only protects spec integrity if every deviating story uses it — Story 1.4 shipped before the pattern was consistently applied, and nothing caught the gap until this retro's acceptance-auditor pass read the frozen text against the actual code side by side.

**D. `Product.Category` is declared `required` (non-nullable) but is `null` on every entity `ProductRepository` fetches.**
- Source: blind-hunter, verified directly.
- Evidence: `Product.cs` declares `public required Category Category { get; set; }`. `ProductRepository.GetByIdAsync`/`GetAllAsync` fetch via `FindAsync`/`AsNoTracking()` with no `.Include(p => p.Category)` — EF materializes the entity via reflection, bypassing the compile-time `required` check, leaving `Category` `null` at runtime on every fetched instance.
- Real-world reachability: **zero today** — verified `ProductMapper.ToDto()` (the only place a fetched `Product` is read back out) touches only `product.CategoryId`, never `product.Category`. `ToEntity()` (used for creates) explicitly sets `Category` from an already-loaded instance, so creates are unaffected.
- Disposition: **defer** — real type-honesty violation (a `required` property that isn't actually always populated is a landmine for future code), but no live trigger path exists in any current call site.
- Upstream lesson: none beyond the general one this project already applies elsewhere — a `required`/non-null annotation is a promise to future readers, and an EF-materialized entity is exactly the kind of code path that can silently break that promise without the compiler ever catching it.

**E. `CorrelationIdMiddleware` trusts the incoming `X-Correlation-Id` header with no validation.**
- Source: blind-hunter and edge-case-hunter, independently.
- Evidence: a whitespace-only header value, or multiple instances of the same header (silently comma-joined by `StringValues.ToString()`), both flow straight into `ILogger.BeginScope` and the echoed response header with no format/length check.
- Disposition: **defer** — real, but low severity (diagnostic-only impact, no security/data consequence); matches the class of low-priority hardening already deferred elsewhere in this project (e.g. `Jwt:ExpiryMinutes`'s missing upper bound).

**F. `CategoryRepository.HasProductsAsync` queries `_context.Products` directly instead of going through `IProductRepository`.**
- Source: blind-hunter, verified directly (`CategoryRepository.cs:53-58`).
- Evidence: one repository reaching into another aggregate's table, inconsistent with the repository-per-aggregate boundary AD-2's rationale describes elsewhere in this codebase.
- Disposition: **defer** — pragmatic given the alternative (adding a cross-cutting method to `IProductRepository` just for this one existence check) isn't obviously better; a real but low-value architectural nitpick, not a correctness issue.
