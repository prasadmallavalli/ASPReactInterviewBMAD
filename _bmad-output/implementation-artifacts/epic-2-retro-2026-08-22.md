## Findings

Per-story diff-scope adversarial review (blind-hunter / edge-case-hunter / verification-gap) already ran for all three stories and is not re-run here (redundant with `2387b19` for 2.1/2.2 and `32cfbec` for 2.3 — user confirmed skipping a duplicate pass on 2.3 earlier this session). This phase instead targets what a per-story review structurally cannot see: the boundaries *between* 2.1→2.2→2.3, and between Epic 2 and its downstream consumer (Epic 3).

**Cross-story boundary (2.2 ↔ 2.3) — verified sound.** The CSRF-token-issuance design changed mid-implementation: the frozen spec-2.2/2.3 intent called for `Login` to mint the `XSRF-TOKEN` cookie, but `DefaultAntiforgery` binds every token to `HttpContext.User`'s identity *at issuance*, and `Login`'s own request is unauthenticated — so a token minted there is bound to no identity and fails every later mutation. The fix (documented in spec-2.3's Spec Change Log and `AuthController.cs`'s doc comments) moved issuance to the `[Authorize]`-protected `Me()` action. This is exactly the kind of defect no single story's isolated review would surface — it only exists at the seam between 2.2 (issues the auth cookie) and 2.3 (needs a correctly-bound CSRF cookie). Confirmed still correct in current code (`AuthController.cs:161`) and covered by `CsrfProtectionTests.RegisterLoginMeThenMutate_NoCsrfHeader400_CorrectCsrfHeaderSucceeds`.

**Cross-epic boundary (Epic 2 → Epic 3) — verified sound.** The `/me`-mints-CSRF-cookie design imposes a contract on any future caller: log in, then call `GET /api/auth/me` once before the first mutation. Epic 3 (built after this design settled) was checked against that contract: `client/src/auth/AuthContext.tsx` calls `/api/auth/me` immediately after a successful login specifically to mint `XSRF-TOKEN` (its own comment cites "Story 2.3"), and `client/src/api/client.ts` reads that cookie and attaches it as `X-CSRF-TOKEN` on every POST/PUT/PATCH/DELETE with `credentials: 'include'`. The contract Epic 2 imposed was correctly honored three epics later — worth recording as a positive, not just an absence of defect, since it's an easy contract to silently violate.

**Diff-range evidence gap (process finding, not a code defect).** The `git-filter-repo` rewrite (2026-08-19, logged in `deferred-work.md`) was necessary to scrub a leaked credential, but its side effect is that Epic 1 and Epic 2's original implementation now share one undifferentiated root commit. Any future retrospective, audit, or `git blame`-based investigation touching Epic 1 or Epic 2 code inherits this same gap. Not remediable after the fact; worth a standing note so nobody spends time hunting for a commit boundary that no longer exists.

**Sprint-status lag (process finding, already fixed this session).** `sprint-status.yaml` showed `2-3-protect-mutation-endpoints-scope-cors: review` from 2026-08-19 through this session despite the spec's own frontmatter saying `status: done` and `32cfbec`'s commit message describing a completed code review. The story was functionally finished and Epics 3–6 were built on top of it in the interim without the tracking file ever being corrected. Fixed in `2387b19`; flagged as a process gap — nothing in the story-closeout step forced the sprint-status write to match the spec-status write.

**Still-open, pre-existing gaps surfaced during Epic 2's reviews (already tracked, not new).** For completeness, these remain open in `deferred-work.md` and are not re-litigated here: `access_token` cookie has no explicit `Expires`/`MaxAge` (session-scoped only); `SameSite=Strict` may not survive a genuinely cross-domain deployment; `AuthController.Me()` has no DB lookup so a deleted/changed user stays valid until token expiry; `CategoryService`'s `HasProducts` 409-branch and `ProductsController`'s status-mapping have zero HTTP-level test coverage (pre-existing since Epic 1, surfaced incidentally by Epic 2's review, not caused by it).
