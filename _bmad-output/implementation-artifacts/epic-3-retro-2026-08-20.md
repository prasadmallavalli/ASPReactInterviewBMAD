## Findings

**What went right, as evidence, not just impression:** every one of the 6 commits in this range went through the same 3-layer per-story review (blind-hunter/edge-case-hunter/verification-gap) during build, catching and fixing 6, 6, 6, 6, 4, and 3 real patch-worthy bugs respectively (31 total) before merge — stale closures, unguarded promise rejections, race conditions, missing validation. The epic-level `bmad-review` pass run for this retro (adversarial + edge-case-hunter + verification-gap, weighted at story boundaries) found comparatively few *new* defects, and its own summary noted: "the diff shows an already well-hardened codebase — most obvious bugs... were caught and fixed during per-story review." The findings below are almost entirely the class of thing only an epic-level, cross-story view can see — not evidence the per-story process was careless.

### Cross-story findings (found only by viewing the whole epic together)

**A. `ProductList`'s Edit and Delete actions have zero mutual awareness for the same row.**
- Sources: verification-gap (Finding 2), edge-case-hunter (Findings 1, 2), adversarial (Findings 1, 2, 3) — 3 of 3 lenses, 6 independent angles on the same root cause.
- Evidence: `ProductList.tsx`'s Edit button (`onClick={() => onEdit(product)}`) has no `disabled` guard tied to that row's `isDeleting`; the Delete button's `disabled={isDeleting}` guard has no corresponding awareness of `App.tsx`'s `editingProduct`; `ProductForm`'s `isSubmitting` (an edit-in-flight PUT) is never surfaced to `ProductList` at all. Clicking Edit on a row whose delete just succeeded shows a form for a product that no longer exists (a 404 on Save, handled gracefully but with no escape besides Cancel); clicking Delete on the row currently open in the edit form removes it server-side while the form keeps showing it as live and submittable.
- Why no single story caught it: 3.4 built Edit before Delete existed; 3.5's own review tested Delete's re-entrancy in isolation, never rendering `ProductForm` and `ProductList` together with overlapping in-flight operations on the same product. `ProductList.test.tsx`'s own delete-in-flight test explicitly asserts *other rows'* buttons stay enabled but never asserts the *same* row's Edit button — the asymmetry shipped with a test that looked adjacent to covering it but didn't.
- Disposition: **defer**. Real, but the correct fix (a shared per-product "busy" signal threaded through `App`/`ProductList`/`ProductForm`) is a design decision, not a one-line patch.
- Upstream lesson: when two mutation actions on the same entity are built in separate stories that never render together in either story's own review, add an explicit cross-action interaction check to the epic-level (not story-level) review pass — this is now demonstrated evidence for why that check belongs here, not in per-story review.

**B. A `refreshKey`-triggered `ProductList` remount can silently drop an in-flight delete's own row-removal.**
- Sources: adversarial (Finding 4), edge-case-hunter (Finding 6) — independently confirmed.
- Evidence: `App.tsx`'s `handleSaved` (from a Create/Edit success) bumps `refreshKey`, which remounts `ProductList` via its `key` prop (Story 3.3's mechanism). If a *different* row's delete is in flight on the old instance at that moment, the remount destroys `deletingIdsRef`/`deletingIds` for that delete. The DELETE request still completes server-side and the old instance's `mountedRef` guard correctly no-ops its response — but the *new* instance has no memory of the pending delete, so the row reappears fully interactive (Delete re-enabled) even though a DELETE for it may still be outstanding, and stays visible until an unrelated future refresh.
- Why no single story caught it: 3.3/3.4's `refreshKey`-remount mechanism and 3.5's self-contained refetch were each reasonable in isolation; nothing in either story's review considered them running concurrently.
- Disposition: **defer**. Narrow (requires a Create/Edit success to land exactly while an unrelated Delete is in flight) and the proper fix is a design decision (don't remount wholesale, or block/queue the `refreshKey` bump while a delete is pending).
- Upstream lesson: same as Finding A — cross-mechanism interaction between stories touching the same component needs an epic-level check.

**C. `ProductForm`'s categories-error and empty-categories branches never render a Cancel button, even in edit mode.**
- Sources: edge-case-hunter (Finding 5), adversarial (Finding 5) — 2 of 3 lenses, independently.
- Evidence: `ProductForm.tsx:332-356`'s two early-return branches (categories fetch failed / resolved empty) render only a heading and an error message, regardless of `mode`. These branches were written for create mode in Story 3.3 (nothing to cancel out of there) and carried over unmodified when 3.4 generalized the component to also handle edit mode.
- Consequence: a user who opens edit mode after (or during) a categories-load failure is stuck with no way back to create mode short of a full page reload.
- Disposition: **fix now** — cheap (add the existing Cancel button to both branches when `mode === 'edit'`), high-confidence.
- Upstream lesson: when generalizing an existing component for a new mode, every early-return branch — not just the happy path — needs an explicit "does this still make sense in the new mode" pass.

**D. The real login → app transition has never been exercised by any automated test.**
- Source: verification-gap (Finding 3).
- Evidence: every `App.test.tsx` scenario that reaches `ProductForm`/`ProductList` mocks `/api/auth/me` as already-200 at mount — none simulate a real, submitted login. `LoginForm.test.tsx` mocks `useAuth()` entirely, never rendering real `AuthContext`. `AuthContext.test.tsx`'s login-path assertions all go through a standalone `Probe` component, never `LoginForm` or `AuthGate`. No Playwright/Cypress/e2e directory exists anywhere in the repo (confirmed by the verification-gap agent's own search) — this gap is not covered elsewhere. This exact flow *was* manually verified once, via `curl`, during the login-form story's own build (recorded in `deferred-work.md`'s entries for that story) — but never captured as an automated regression test.
- Disposition: **fix now** as a test addition — extend `App.test.tsx` with one more scenario: start `unauthenticated`, submit the real `LoginForm`, let the real `AuthContext.login()` two-step flow run, assert `AuthGate` swaps to the product views, then continue into the existing create→edit→delete sequence.
- Upstream lesson: when an unplanned "prerequisite" story gets bolted mid-epic, its test coverage should explicitly include the *seam* it creates (here: auth→app), not just its own isolated behavior.

**E. The stale-response guard in `ProductForm` is only tested starting from edit mode, never from a create-mode submission switching to edit mid-flight.**
- Source: verification-gap (Finding 1).
- Evidence: both existing stale-response tests (`ProductForm.test.tsx:503-565`, `:571-615`) `render` with `mode="edit"` initially. No test starts a create submission, then switches the same instance to edit before the POST resolves — a real, reachable sequence, since `ProductList`'s Edit button is never disabled while a create submission is in flight (see Finding A).
- Disposition: **fix now** as a test addition — mirrors the existing pattern, starting from `mode="create"` instead.

### Pattern-divergence and cleanup findings

**F. `AuthContext`'s mount-time session check claims parity with `ProductList`'s stale-response guard but is actually weaker.**
- Source: adversarial (Finding 6).
- Evidence: `AuthContext.tsx`'s doc comment explicitly says "same pattern as ProductList's mountedRef" — but `ProductList.fetchProducts` additionally uses a `requestIdRef` generation counter to reject a stale, out-of-order response, which `AuthProvider` lacks. The claim of parity does not hold up against the actual code.
- Real-world reachability: low in this app's current architecture — `AuthProvider` mounts exactly once at the app root and is never remounted during normal operation (unlike `ProductList`, which remounts by design). The gap is real but the trigger (rapid remount/StrictMode double-invoke racing two `/me` calls) has no live code path today.
- Disposition: **defer** — real inconsistency, worth fixing for correctness and to make the comment's claim true, but not urgent given near-zero practical reachability.
- Upstream lesson: a comment claiming "same pattern as X" should be verified against X at review time, not just trusted.

**G. Four unused Vite-scaffold files remain in the repo, imported by nothing.**
- Source: adversarial (Finding 9), independently confirmed by this retro's own aggregate-view pass (`App.tsx`'s import list does not include `App.css`, and nothing imports the three `assets/*` files).
- Evidence: `client/src/App.css`, `client/src/assets/hero.png`, `client/src/assets/react.svg`, `client/src/assets/vite.svg` — all present since Story 3.1's scaffold, carried through all 6 commits, never referenced.
- Disposition: **fix now** — trivial, zero-risk deletion.
- Upstream lesson: a "does this file get used" sweep belongs in the checklist for scaffold-heavy first stories.

**H. Client-side price validation checks the lower bound and finiteness but not the upper bound.**
- Source: adversarial (Finding 10).
- Evidence: `ProductForm.tsx`'s JS-level guard checks `!Number.isFinite(parsedPrice) || parsedPrice <= 0` but has no `parsedPrice > 1_000_000` check, even though the native `max="1000000"` attribute encodes that ceiling and the test suite itself proves native constraints are bypassable (`fireEvent.submit` is used specifically to exercise the JS-level guards in isolation).
- Disposition: **fix now** — trivial, one-line extension of an existing condition, restores symmetry with the already-established defense-in-depth pattern.

**I. `describeError`/`describeAuthError` is now duplicated three ways, not two.**
- Source: this retro's own duplication-map pass (`grep` confirms `function describeError` defined separately in `ProductList.tsx`, `ProductForm.tsx`, and as `describeAuthError` in `AuthContext.tsx`, ~14 near-identical lines each).
- Context: the 3.4 review already logged the `ProductList`↔`AuthContext` two-way duplication as deferred ("no coupling reason yet"). The 3.3→3.4 `ProductForm` generalization added a third copy, crossing into territory the original deferral didn't anticipate.
- Disposition: **defer**, but re-flagged with updated count — 3 call sites is a materially stronger case for extraction (a shared `client/src/api/describeApiError.ts`) than the 2-site case already on record.
- Upstream lesson: when deferring a "not worth extracting yet" duplication, note the current instance count explicitly so the next reviewer (or a retro) can see when a threshold is crossed, instead of re-deriving the count from scratch.

**J. No re-authentication trigger on a mid-session 401 (session/cookie expiry).**
- Source: adversarial (Finding 7).
- Disposition: **accept as already-tracked** — this is the same gap already logged in `deferred-work.md` against the login-form prereq spec ("nothing re-checks the session after mount-time `/api/auth/me`"). No new action; confirmed still open in that ledger.

**K. No `scrollIntoView`/focus when entering edit mode on a long list.**
- Source: adversarial (Finding 11).
- Disposition: **defer** — matches the a11y/focus-management deferred pattern already established and logged for every prior Epic 3 story (`ProductList`, `LoginForm`, `CreateProductForm`/`ProductForm` all carry the same class of deferred finding).

### Spec-to-implementation reconciliation

**L. The login-form prerequisite was never in `epics.md`'s Epic 3 story list.**
- Evidence: `epics.md`'s Epic 3 declares only Stories 3.1–3.5; none mention authentication UI, even though Story 3.3 (Create Product) strictly requires an authenticated session with a CSRF token that only Epic 2's backend provides — no story ever specified how the *frontend* would obtain one. This was caught during this session's own investigation before drafting 3.3's spec, resolved via an explicit multi-goal split (user-approved) into an ad-hoc, unnumbered spec (`spec-epic-3-prereq-login-form.md`) that sits outside the normal `sprint-status.yaml` story list to this day.
- Disposition: **propose spec reconciliation** — `epics.md` should be updated to formally record the login-form story as delivered Epic 3 scope (a new Story 3.0 or equivalent), so a future reader doesn't see a phantom gap between "Epic 2 built auth" and "Epic 3 assumes auth exists" with no visible bridge. Human decision required; not applied here.
- Upstream lesson: epic-level planning should explicitly cross-check that a frontend epic accounts for whatever backend session/auth mechanics its own mutation-flow ACs implicitly require.

**M. `client/src/auth/` is a new top-level directory not in the originally-declared structural convention.**
- Evidence: `epic-3-context.md`'s Technical Decisions declared only `client/src/api/` and `client/src/components/`; `auth/` emerged during the login-form story, self-documented in that spec's own Code Map as "mirroring `api/`/`components/`."
- Disposition: **accept as-is** — sensible, well-justified, already self-documented. Recorded here so a later retro doesn't re-flag it as an unexplained deviation.
