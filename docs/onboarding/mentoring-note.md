# Onboarding Note: Welcome to ASPFullStackBMAD

Status: Active · Date: 2026-08-20 · Author: Prasadmallavalli

Written for a mid-level engineer joining this codebase — you already know your way around C#/ASP.NET Core and React, this note is about *this* codebase's specific choices, not general practice. It's a mentoring conversation in document form, not a spec.

**Two numbering schemes, so you're not confused the first time you see both:** `AD-#` (e.g. AD-2, AD-4, AD-8) is the terse decision log in `ARCHITECTURE-SPINE.md`. `ADR-###` (e.g. ADR-001, ADR-006) is the fuller Context/Decision/Alternatives/Consequences writeup under `docs/adr/`, added later for a subset of those same decisions. Where both exist, the `ADR-###` is the better read.

**A quirk of this repo's history you'll hit the first time you run `git blame`:** it was `git init`'d partway through the build — `f1bc57f` is one "Initial commit" bundling everything through Story 2.2's code, not a per-story history. Story 2.3's commit (`32cfbec`) is the actual point where one-commit-per-story starts.

## Getting started

Backend: `dotnet build` / `dotnet test` from the repo root (`ASPFullStackBMAD.sln`); `docker-compose up` brings up SQL Server first. Frontend: `cd client && npm run dev` (Vite dev server), `npm test` (Vitest), `npm run build` (typecheck + build), `npm run lint`. There's no consolidated setup README yet — that's a known, already-logged gap (`deferred-work.md`, Story 1.1 section), not something you missed.

## The shape of the thing

Four backend projects — `Domain`, `Application`, `Infrastructure`, `Api` — plus a React client. The dependency direction only ever points inward: `Api` depends on `Application`, `Application` depends on `Domain`, `Infrastructure` implements `Domain`'s interfaces. `Domain` depends on nothing. If you ever find yourself typing `using Microsoft.EntityFrameworkCore;` in a file under `Application` or `Api`, stop — that's a real rule here (AD-2), not a suggestion, and it means you're about to reach for something that belongs in `Infrastructure` instead.

## Why the code looks the way it does

**Repository + Unit of Work, and why the interfaces are narrow.** `ICategoryRepository`/`IProductRepository` aren't a generic `IRepository<T>` — that was considered and rejected early (see [ADR-001](../adr/001-repository-and-unit-of-work.md)) because Category and Product don't have the same query needs (`HasProductsAsync` only makes sense for Category). This is Interface Segregation in practice, not a textbook exercise: each interface is shaped by what its consumers actually call, not by what a generic contract could theoretically support. The bigger reason the abstraction exists at all is Dependency Inversion — `CategoryService` depends on `IUnitOfWork`, an abstraction, never on `AppDbContext`, the concrete EF Core type. That's also what makes `Application.Tests` possible without a real database (mock `IUnitOfWork` with Moq).

Worth saying honestly, the way a mentor would rather than a textbook: at this project's size (two related entities, one developer), injecting `AppDbContext` directly would have worked fine too. The abstraction's payoff is testability and legibility, not solving a live scaling problem — ADR-001 says this outright. Don't take that as license to skip the pattern; it's the established convention here and Moq-based tests already depend on it existing.

**Service layer, one per entity.** `CategoryService`/`ProductService`/`UserService` each own one entity's business rules, and nothing else — a controller never talks to a repository directly, and a repository never contains business logic (just EF Core query shape). That's Single Responsibility doing real work: when a business rule changes, you know which one file to open.

**Manual DTO mapping, not AutoMapper.** Every mapper (`CategoryMapper`, `ProductMapper`, `UserMapper`) is hand-written extension methods. This was a deliberate call, not an oversight — see [ADR-002](../adr/002-manual-dto-mapping.md). The upside you'll notice immediately: `UserMapper.ToDto()` visibly never touches `PasswordHash`, because someone had to type that mapping by hand and chose not to. The honest downside: at three entities, hand-writing mappers is barely less code than configuring AutoMapper would be. This doesn't scale gracefully — if this project grew to two dozen entities, revisit it.

**A note on SOLID, since I mentioned two of the five above:** Dependency Inversion and Interface Segregation are the two principles genuinely load-bearing in this codebase. Single Responsibility shows up in the service-per-entity split. Open/Closed and Liskov Substitution aren't really exercised here — there's no inheritance hierarchy in the domain model (`Category`/`Product`/`User` are all independent, unrelated classes), so don't go looking for a textbook example of either. That's not a gap; it's just not the shape of this problem.

## Things to watch out for

**1. DI lifetimes — read this one first.** In Story 1.5, `IProductRepository` was deliberately registered `AddSingleton` instead of `AddScoped`, on purpose, to see what would happen under load. 48 of 50 concurrent requests failed with `System.InvalidOperationException` — EF Core's `ConcurrencyDetector` catching the Scoped `AppDbContext` being reused unsafely by every request, because the Singleton-lifetime repository held onto one instance for the app's entire life. Reverting to `AddScoped` produced 50/50 clean responses, twice. Full trace: [`story-1-5-di-bug-log-excerpt.md`](../../_bmad-output/implementation-artifacts/story-1-5-di-bug-log-excerpt.md); full writeup: [ADR-006](../adr/006-scoped-di-lifetimes.md). The guardrail now in place (`ValidateScopes`/`ValidateOnBuild` enabled outside Development too) catches this class of mistake at startup — but it only catches it if someone actually starts the app in a way that exercises it. ADR-006 is explicit that there's still no automated regression test or DI-container lifetime assertion backing this up — a future revert of `Program.cs` with the app never actually started wouldn't be caught by anything. That's a legitimate, well-scoped first task if you're looking for one. If you ever add a new repository or service registration, say the lifetime out loud to yourself: does this hold a `DbContext`, directly or transitively? If yes, it's `Scoped`. This is the single most concrete "here's what happens if you get this wrong" example in the codebase — worth internalizing, not just reading once.

**2. Check-then-act races exist, and they're accepted, not hidden.** `CategoryService.DeleteAsync` checks `HasProductsAsync`, then deletes — if a Product is inserted in between, the DB's FK-restrict still stops the actual delete, but the caller gets an unhandled 500 instead of a clean 409 in that narrow window (see [ADR-005](../adr/005-category-delete-conflict-no-cascade.md) for the full reasoning behind the 409-vs-cascade choice this race sits inside). Same shape of gap exists in Product create/update (stale Category check) and User registration (stale email-uniqueness check). This is a direct consequence of AD-2: `Application` can't catch `DbUpdateException` because that type lives in EF Core, and Application isn't allowed to depend on EF Core. The real fix (a Domain-level exception type Infrastructure translates) was identified and deliberately not built — it's a small design decision outside any one story's approved scope. If you're the one who eventually builds it, it needs to happen once, consistently, across all three services — not as a one-off patch to whichever race you personally tripped over.

**3. `[Required]` doesn't mean what you'd assume.** `CategoryRequestDto.Name`/`ProductRequestDto.Name` both accept whitespace-only strings today — `[Required]` only rejects null/empty, not `"   "`. This is the sharp edge of AD-8's Data-Annotations choice (see [ADR-004](../adr/004-data-annotations-validation.md)): `[Required]` is fine for presence/length/range, but it doesn't compose into "trimmed and non-blank" on its own. If you're adding a new required string field anywhere, don't assume `[Required]` alone gives you a real non-blank guarantee; it doesn't, and this codebase already has two live examples of that gap going unnoticed until review.

**4. The login cookie and the CSRF token are minted at different times, on purpose.** `POST /api/auth/login` sets the `access_token` cookie but does *not* mint the CSRF token — `AuthContext.login()` has to make a follow-up call to `GET /api/auth/me` specifically to get one, because `DefaultAntiforgery` binds tokens to the caller's identity at issuance, and the Login request itself is still unauthenticated when it runs. That specific mechanic is settled ASP.NET Core behavior, not a bug to "simplify" away — but don't take that as "the CSRF design here is fully written up": [ADR-003](../adr/003-httponly-cookie-token-storage.md) (the cookie-storage decision that makes CSRF a problem in the first place) is explicit that the CSRF/anti-forgery mechanism itself still has no ADR of its own — it's a logged, open documentation gap in `deferred-work.md`, not a closed topic.

**5. Secrets landed in git history once — know that before you trust an old clone.** The real SQL Server `sa` password and JWT signing key were committed in plaintext from this repo's very first commit (`docker-compose.yml`, `appsettings.Development.json`). Both were later rotated and the old values were scrubbed from git history entirely via `git-filter-repo` plus a force-push (see [`docs/review/code-review-checklist.md`](../review/code-review-checklist.md), Item 10, for the full remediation trail). Practical implication for you: if you ever have an old clone, fork, or local branch from before that rewrite, its history still has the old (now-rotated, so low-risk, but still real) values in it — don't assume every copy of this repo has clean history.

**6. React fetch effects need a stale-response guard, every time — but "the same pattern" is an overstatement; check which one actually applies.** `ProductList.tsx` uses a `requestIdRef` generation counter to drop a response that's no longer the latest one in flight — established in Story 3.2 after a real race was found in review. `ProductForm.tsx` uses a different, key-based guard (`targetKeyRef`) suited to its create/edit-mode-switching shape. `AuthContext.tsx` only has a `mountedRef` — no generation counter — which means a real, if narrow, gap still exists there: if the mount-time `GET /api/auth/me` check is still in flight when the user submits `login()`, both fire independent `/me` calls with nothing ordering them, so the slower response could overwrite the newer state. If you add a new `fetch`-in-`useEffect`, pick the guard shape that matches what can race in your component — don't assume one pattern fits every case, and don't assume `AuthContext` is already protected the way `ProductList` is.

`ProductList.tsx` has its own adjacent open gap worth knowing before you touch it: no test (or handling) covers a DELETE that succeeds followed by a refresh that then fails — right now that flips the whole view to the generic fetch-error screen with no indication the delete actually worked ([`docs/review/code-review-checklist.md`](../review/code-review-checklist.md), Item 13).

**7. Timing side channels are a known, accepted gap on the auth endpoints — not something we pretend doesn't exist.** `UserService.LoginAsync`'s unknown-email branch returns immediately, while the wrong-password branch first runs `VerifyHashedPassword` (deliberately slow). Both return the same 401 body, but the extra work on one path is a measurable timing difference. Low real-world risk for this project's current scale; worth knowing about before you assume the identical-401 design fully closes email enumeration.

**8. Two quieter gaps worth knowing before you touch the controllers.** `CategoryService.DeleteAsync`'s 409 branch and `ProductsController`'s result-to-HTTP-status mapping (`CategoryNotFound`→400, `NotFound`→404) both have zero controller-level test coverage — every existing test would still pass if either mapping were silently inverted (checklist Item 11). And neither `CategoriesController` nor `AuthController` declares `[ProducesResponseType]`, so the generated OpenAPI spec only documents the default success response, not the 404/409/401 outcomes these endpoints actually produce (checklist Item 14). Neither is urgent, but both are easy to make worse without noticing if you're not looking for them.
