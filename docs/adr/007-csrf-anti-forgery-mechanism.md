# ADR-007: CSRF Protection via ASP.NET Core's Built-In IAntiforgery, Issued from `Me()` Not `Login`

Status: Accepted
Date: 2026-08-19 (Story 2.3) · Deciders: Prasadmallavalli
This is the CSRF half of AD-5 in `ARCHITECTURE-SPINE.md` — the second control [ADR-003](003-httponly-cookie-token-storage.md)'s cookie decision required.
Previously logged as a gap in [`deferred-work.md`](../../_bmad-output/implementation-artifacts/deferred-work.md) and as an open item on the [Epic 2 retrospective](../../_bmad-output/implementation-artifacts/epic-2-retro-2026-08-22.md); written up here.

## Context

[ADR-003](003-httponly-cookie-token-storage.md) delivers the JWT as an `httpOnly` cookie so client-side JavaScript can never read or exfiltrate it. That closes XSS-based token theft, but it reopens a different gap: a browser attaches an `httpOnly` cookie to *every* request to the API's origin automatically, including ones triggered by a malicious third-party page the user happens to have open — the textbook CSRF setup. `SameSite=Strict` was already doing most of that mitigation work as an unstated interim measure before this decision, but Story 2.3's own acceptance criteria required an explicit, server-validated CSRF/anti-forgery token on every mutating request, not an implicit byproduct of a cookie attribute.

## Decision

Mutation endpoints are protected by ASP.NET Core's built-in `IAntiforgery`, wired as follows:

- **Global validation, not per-action.** `AutoValidateAntiforgeryTokenAttribute` is registered once as a filter in `AddControllers(options => ...)` (`Program.cs`). Its built-in safe-method exemption means it only ever checks POST/PUT/PATCH/DELETE — GET/HEAD/OPTIONS/TRACE are exempt automatically, mapping exactly onto "mutation-only" protection with zero per-action annotation. (It needs `AddMvcCore().AddViews()` present in DI to resolve — a non-obvious dependency, called out directly in `Program.cs`'s comments.)
- **`Register`/`Login` are explicitly exempted** via `[IgnoreAntiforgeryToken]`. CSRF protection exists to stop a malicious page from riding an *existing* authenticated session; before login, there is no session to ride, and requiring a token the client cannot yet possess would make login itself impossible.
- **Token issuance happens in `Me()`, not `Login`** — this is the decision's non-obvious part, and it was reached by reverting an earlier attempt. The frozen story spec originally called for `Login` to call `IAntiforgery.GetAndStoreTokens(HttpContext)` right after setting the `access_token` cookie. Verified empirically against a real HTTPS run that this does not work: `DefaultAntiforgery` unconditionally binds every issued token pair to `HttpContext.User`'s identity *at issuance time*, and the request running `Login` is itself unauthenticated (no `access_token` cookie arrived on the way in — the same reason `[IgnoreAntiforgeryToken]` is needed on `Login` at all). A token minted mid-`Login` is therefore bound to "no identity," while every later mutation request *is* authenticated — a mismatch that failed every subsequent mutation with "the provided antiforgery token was meant for a different claims-based user than the current user," regardless of the header sent. The fix moves `GetAndStoreTokens(HttpContext)` into the pre-existing `[Authorize]`-protected `GET /api/auth/me`, which only ever runs once `HttpContext.User` is the same identity every later mutation request will present.
- **A distinct, JS-readable `XSRF-TOKEN` cookie is set explicitly** in `Me()`, holding `tokens.RequestToken`. The framework's own internal antiforgery cookie keeps its default name and stays `HttpOnly` — it is not renamed or exposed to JavaScript, because the cookie-token and request-token halves of an antiforgery pair are cryptographically related but not interchangeable; making the framework's own cookie JS-readable and reusing its value fails validation with "the cookie token and the request token were swapped." The client echoes `XSRF-TOKEN`'s value back as an `X-CSRF-TOKEN` header on every mutating request, which `AutoValidateAntiforgeryTokenAttribute` is configured to read.

Net effect: a client must call `GET /api/auth/me` once after a successful login, before its first mutation, to receive the `XSRF-TOKEN` cookie. Epic 3's frontend (`AuthContext.tsx`) implements exactly this sequence.

## Alternatives

- **Hand-rolled CSRF token (custom generate/store/validate).** Rejected — `IAntiforgery` ships in the shared framework already referenced by `Microsoft.NET.Sdk.Web`, at zero new NuGet cost, matching the project's standing preference for framework-provided pieces over custom implementations (the same reasoning already applied to `PasswordHasher<User>` in Story 2.1 and `JwtBearer` in Story 2.2).
- **Issue the CSRF token during `Login` itself.** This was the original design and was implemented first. Rejected after empirical verification showed the identity-binding failure described above — every mutation failed CSRF validation regardless of the header sent, because the token was bound to no identity at issuance.
- **Rename the framework's own antiforgery cookie to `XSRF-TOKEN` and make it `HttpOnly = false`**, instead of setting a second cookie manually. Rejected — this repurposes the framework's internal cookie-token half as the client-facing request-token half, which are not interchangeable; doing so breaks validation with a distinct "cookie token and request token were swapped" error.
- **A dedicated `GET /api/auth/csrf-token` bootstrap endpoint.** Rejected as unnecessary surface area — the only place a client legitimately needs a CSRF token is right after establishing a session, and `Me()` already exists as an `[Authorize]`-protected "who am I" endpoint for that purpose. No unauthenticated flow in this app needs to mutate anything, so a separate bootstrap endpoint would sit unused.

## Consequences

- Zero new NuGet dependencies — `IAntiforgery` ships in the ASP.NET Core shared framework.
- The client-server contract is stricter than "log in, then mutate": any caller — the current React SPA or a future client — **must** call `GET /api/auth/me` once after login before its first mutation, or every mutation will 400 with a missing/invalid CSRF token. This is a real behavioral requirement, not just documentation, and is easy to violate silently if a future client is built without reading this ADR. (Confirmed honored by Epic 3's `AuthContext.tsx` in the [Epic 2 retrospective](../../_bmad-output/implementation-artifacts/epic-2-retro-2026-08-22.md).)
- `Register` and `Login` remain permanently unauthenticated *and* CSRF-unprotected by design — acceptable because no session exists yet to ride, but it means these two endpoints have no CSRF defense of their own and rely on other protections (e.g. rate limiting) that are not currently implemented; out of this decision's scope, not a defect it introduces.
- The anti-forgery token is the explicit second control AD-5 calls for, alongside `SameSite=Strict` on both the `access_token` and `XSRF-TOKEN` cookies — matching [ADR-003](003-httponly-cookie-token-storage.md)'s stated tradeoff (XSS protection traded for a CSRF exposure that needed a dedicated second control to close).
- Regression coverage: `CsrfProtectionTests.RegisterLoginMeThenMutate_NoCsrfHeader400_CorrectCsrfHeaderSucceeds` exercises the full register → login → `/me` → mutate-without-header (400) → mutate-with-header (success) sequence, guarding specifically against the identity-binding regression this decision fixed.
- Known, already-tracked gap (unrelated to this decision, but adjacent): `SameSite=Strict` may not survive a genuinely cross-domain — not just cross-port — frontend/API deployment; not a current deployment target, logged in `deferred-work.md` for revisit if that changes.
